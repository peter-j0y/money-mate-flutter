# 기능 기획 (money_mate)

새 기능·정책 변경을 **기존 정책(통합 기획서)과 실제 구현(코드)에 근거해** 기획하고, 모호한 부분은 전부 사용자에게 되물어 구체화한 뒤, 검토가 끝나면 "배포 대기" 기획안으로 보관했다가 **배포가 완료되면** 통합 기획서에 반영하는 스킬이다.

이 스킬은 두 가지 모드로 동작한다:

- **기획 모드** (1~6단계): "○○ 기획해줘" 류의 요청. 기획안을 확정해 배포 대기 상태로 보관하는 데서 끝난다. **통합 기획서는 건드리지 않는다.**
- **배포 반영 모드** (7단계): "v1.4.0 배포 완료됐어", "통합 기획서 반영해줘" 류의 요청. 해당 버전에 포함된 배포 대기 기획안을 실제 배포 코드와 대조해 통합 기획서에 반영한다.

핵심 원칙 네 가지:

1. **근거 없이 쓰지 않는다.** 모든 요구사항은 통합 기획서의 어느 절, 또는 코드의 어느 파일과 어떻게 맞물리는지 설명할 수 있어야 한다.
2. **추측으로 빈칸을 채우지 않는다.** 결정이 필요한 지점은 반드시 사용자에게 묻는다. 추천안은 제시하되 확정은 사용자가 한다.
3. **통합 기획서는 "배포된 앱의 현재 상태"만 담는다.** 검토가 끝났더라도 배포 전 기획은 반영하지 않는다. 배포 전 기획이 섞이면 다른 기획 검증 시 "현재 동작"과 "예정 동작"이 구분되지 않는다.
4. **승인 없이 통합 기획서를 고치지 않는다.** 통합 기획서는 다른 기획 검증의 기준 문서라, 잘못 반영되면 이후 모든 기획이 오염된다.

## 0. 참고 자료 위치

- **통합 기획서(Notion)**: `reference` 메모리 `integrated-spec-money-mate`에 링크가 있다 (현재 `https://app.notion.com/p/3bad4d2df2e281f7a4ccc88ee7346d70`). 메모리에 없으면 사용자에게 링크를 묻고 메모리로 저장한다.
- **상위 워크스페이스 페이지**: 머니메이트 (`https://app.notion.com/p/20ad4d2df2e280f0918bc06791ee06f4`)
- **기획안 보관 위치**: 머니메이트 페이지 하위의 개별 Notion 페이지 (icon `📝`, 제목은 기능명만). 페이지 상단의 `**상태**`(`확정 · 배포 대기` / `배포 완료 · 통합 기획서 반영됨` / `보류` / `폐기`)와 `**대상 버전**`(예: `v1.4.0`)으로 관리한다. 배포 대기 기획안은 `notion-search`로 "확정 · 배포 대기"를 검색해서 찾는다.
- **릴리즈 규칙**: 릴리즈마다 `vX.Y.Z` 이름의 브랜치와 태그가 함께 존재한다. 이름이 ambiguous하면 `refs/tags/vX.Y.Z`, `refs/heads/vX.Y.Z`처럼 풀네임을 쓴다.
- **코드 진입점**:
  - DB 스키마/마이그레이션: `lib/data/local/app_database.dart` (`schemaVersion`, `MigrationStrategy`)
  - 엔티티: `lib/data/model/entities/`
  - Repository: `lib/data/repositories/` (`*_repository.dart` + `*_repository_impl.dart`)
  - ViewModel: `lib/ui/<feature>/view_models/`
  - 통화 관련: `lib/ui/core/currency/`
  - 다국어 문자열: `lib/l10n/app_ko.arb`, `lib/l10n/app_en.arb`
  - 설정/리마인더: `lib/ui/more/`
- **기획 문서 뼈대**: `templates/plan_template.md`

# 기획 모드

## 1. 요청 파악

사용자가 준 요청을 한두 문장으로 재진술하고("이렇게 이해했습니다: …") 기획 대상의 범위를 확인한다. 이 시점에는 세부를 묻지 않는다 — 2단계 조사를 먼저 해야 질문의 질이 올라간다. 단, 요청 자체가 무엇인지조차 불분명하면(예: "알림 좀 개선해줘") 그것만 먼저 묻는다.

## 2. 기존 정책·구현 조사 (필수, 생략 금지)

질문하기 **전에** 아래를 모두 수행한다.

### 2-1. 통합 기획서 읽기

`notion-fetch`로 통합 기획서 전체를 읽는다. 현재 버전(`**버전**: vN`), 관련 절, 그리고 특히:
- **8. 크로스커팅 정책: 통화 처리** (⚠️ callout) — 반복 수정 이력이 있는 가장 민감한 정책
- **10. 신규 기획 검증 체크리스트** — 하나라도 해당되면 8절과의 충돌을 명시적으로 검토

### 2-2. 배포 대기 기획안 확인

통합 기획서에는 아직 배포되지 않은 확정 기획이 들어 있지 않다. 그래서 `notion-search`로 상태가 `확정 · 배포 대기`인 기획안을 찾아서, 이번 기획과 같은 화면·데이터·정책을 건드리는 것이 있으면 읽는다. 충돌하거나 겹치면 3단계에서 질문한다(예: "v1.4.0에 배포 대기 중인 「자산 메모」 기획이 같은 Assets 테이블에 필드를 추가합니다. 마이그레이션 순서를 어떻게 할까요?").

### 2-3. 실제 코드 확인

통합 기획서는 스냅샷이라 코드와 어긋나 있을 수 있다. **관련 기능의 실제 코드를 직접 읽어서** 확인한다:
- 관련 엔티티·테이블 필드, 현재 `schemaVersion`
- 관련 ViewModel의 검증 로직(예: 금액 > 0, 즐겨찾기 최대 5개 같은 규칙이 코드 어디에 있는지)
- 관련 화면의 진입 경로와 현재 UI 흐름
- 관련 arb 키 (기존 문구 재사용 가능 여부)
- `git log --oneline -20 -- <관련 경로>`로 최근 변경 이력 — 반복 수정된 영역은 민감 영역이다

조사 범위가 넓으면(여러 기능에 걸친 변경 등) Explore 서브에이전트에게 "관련 파일과 규칙 위치만" 찾게 하고 결론만 받아온다.

### 2-4. 조사 결과 요약 공유

질문에 들어가기 전에 사용자에게 짧게 공유한다:

```
## 현황 조사 결과
- 관련 정책: 통합 기획서 §3, §8-2 (자산 신규 입력 KRW 고정) …
- 현재 구현: `lib/ui/asset/view_models/xxx.dart:42` 에서 … 
- 배포 대기 기획: 「자산 메모」(v1.4.0) — Assets 테이블 공유 (있을 때만)
- ⚠️ 기획서-코드 불일치: 기획서는 X라고 하지만 코드는 Y (있을 때만)
- ⚠️ 정책 충돌 가능성: 이번 요청은 §8-2와 충돌할 수 있음 — 아래에서 질문드립니다
```

기획서와 코드가 다르면 **코드가 현재 사실**이다. 불일치는 기획안의 "통합 기획서 영향" 절에 기록해 두고, 7단계 배포 반영 때 함께 바로잡는다.

## 3. 모호성 해소 인터뷰 (필수)

### 3-1. 미결 사항 목록 만들기

조사 결과를 바탕으로 아래 체크리스트를 훑어 **결정되지 않은 항목**을 전부 뽑아 목록화한다. 해당 없는 항목은 건너뛴다.

| 영역 | 확인할 것 |
|---|---|
| 목적 | 해결하려는 사용자 문제, 성공 판단 기준 |
| 진입점/UI | 어느 탭/화면에서 어떻게 들어가는가, 버튼·메뉴 위치, 화면 전환 방식 |
| 동작 규칙 | 입력값 검증(최소/최대, 0, 음수, 빈 값), 개수 제한, 정렬·필터 기준 |
| 상태 | 빈 상태, 로딩, 에러 시 표시, 취소/뒤로가기 시 동작 |
| 데이터 | 새 필드·테이블 필요 여부, nullable/기본값, `schemaVersion` 증가 및 기존 데이터 마이그레이션(백필 값) |
| 기존 데이터 호환 | 이미 저장된 기록·즐겨찾기·자산에 어떻게 적용되는가 (소급 적용 여부) |
| 통화 (§8) | 어떤 통화로 저장·표시하는가, 합산이 발생하는가, 주 통화 영향 범위가 바뀌는가 |
| 포트폴리오 (§6) | 비율·합계 계산식에 영향이 있는가 |
| 알림 (§5) | 알림 ID·예약 규칙과 충돌하는가 |
| 다국어 | 새 문구의 한/영 표기, 미지원 언어 폴백 |
| 디자인 | 색상 토큰(라이트/다크), 기존 공용 위젯 재사용 여부 |
| 범위 | 이번에 하지 **않는** 것 (Out of scope) |
| 대상 버전 | 어느 릴리즈(`vX.Y.Z`)에 포함할 예정인가 — 7단계에서 이 값으로 기획안을 찾는다 |

### 3-2. 질문하는 방법

- **선택지가 있는 결정은 `AskUserQuestion`** 으로 묻는다. 추천안을 첫 번째 옵션에 두고 라벨 끝에 `(Recommended)`를 붙이며, description에 **왜 추천하는지 + 기존 정책/코드와의 관계**를 적는다. UI 배치처럼 시각 비교가 필요하면 `preview`에 ASCII 목업을 넣는다.
- 한 번에 최대 4개 질문까지 묶을 수 있다. 서로 의존적인 질문은 묶지 말고 앞의 답을 받은 뒤 다음을 묻는다.
- **자유서술이 필요한 내용**(배경, 문제 상황, 문구 등)은 `AskUserQuestion` 대신 일반 대화로 묻는다.
- 정책 충돌이 있으면 반드시 별도 질문으로 분리한다: "이번 기획은 §8-2(자산 신규 입력 KRW 고정)와 충돌합니다. ① 정책을 의도적으로 변경 ② 요구사항을 정책에 맞게 조정 — 어느 쪽인가요?" 정책 변경을 택하면 그 정책에 의존하는 다른 규칙(예: §6 포트폴리오 단순 합산)까지 연쇄 영향을 질문한다.
- 사용자의 답변은 다음 턴 첫머리에 재진술한 뒤 반영한다.

### 3-3. 종료 조건

미결 사항 목록이 **0개**가 될 때까지 라운드를 반복한다. 사용자가 "그건 알아서 정해줘"라고 하면 추천안을 채택하되 기획안에 `가정(사용자 위임)`으로 표시해 검토 단계에서 다시 보이게 한다. 사용자가 "지금은 미정"이라고 하면 `미결`로 남기고, 미결 항목이 남은 기획은 `확정 · 배포 대기`로 보관할 수 없다고 알린다.

**절대 하지 말 것**: 묻지 않고 그럴듯한 값으로 채워 넣기, 정책 충돌을 조용히 우회하기, 모호한 표현("적절히", "필요 시", "등")을 기획안에 남기기.

## 4. 기획안 작성

`templates/plan_template.md` 뼈대로 기획안을 작성해 **채팅에 먼저 보여준다**. 작성 기준:

- 모든 규칙은 테스트 가능한 문장으로 쓴다. ("금액 입력" ✗ → "금액은 1 이상의 정수, 빈 값이면 저장 버튼 비활성화" ✓)
- 각 요구사항에 근거를 단다: `근거: 통합 기획서 §3` / `근거: lib/ui/asset/...:42` / `근거: 사용자 결정(라운드 2)`
- **통합 기획서 영향** 절에는 배포 후 어느 절을 추가/수정/삭제할지, 바뀌기 전·후 문장을 구체적으로 적는다 — 이것이 7단계 반영의 입력이 된다.
- 구현 영향(파일·마이그레이션·arb 키)은 개략만 적는다. 이 스킬은 기획까지이며 구현하지 않는다.

## 5. 검토 루프

기획안을 보여준 뒤 사용자에게 수정 사항을 받는다. 수정 요청이 새 모호성을 만들면 3단계로 돌아가 다시 묻는다. 수정 반영 후에는 바뀐 부분만 diff처럼 요약해서 보여준다.

**검토 완료 판단**: 사용자가 명시적으로 "확정/검토 완료"라고 말해야 한다. 침묵이나 "괜찮네" 정도로는 확정으로 간주하지 말고 `AskUserQuestion`으로 확인한다:
- "검토 완료 — 배포 대기로 보관" (Recommended)
- "보류"
- "추가 수정 필요"

## 6. 배포 대기 기획안 보관

검토가 완료되면 **통합 기획서가 아니라** 기획안 페이지로 보관한다.

1. `notion-create-pages` 호출 전에 `notion-fetch`로 `notion://docs/enhanced-markdown-spec`을 읽는다. 문법을 추측하지 않는다.
2. 머니메이트 페이지 하위에 기획안 페이지를 만든다. 제목은 기능명만, icon은 `📝`이다. 본문 맨 위에 `**상태**: 확정 · 배포 대기`, `**대상 버전**: vX.Y.Z`, `**확정일**: YYYY-MM-DD`를 넣는다. 같은 기능의 기획안 페이지가 이미 있으면 새로 만들지 않고 그 페이지를 갱신한다.
3. 생성한 링크를 전달하고 이렇게 안내한다: "이 기획은 vX.Y.Z 배포가 완료된 뒤 통합 기획서에 반영합니다. 배포가 끝나면 'vX.Y.Z 배포 완료'라고 알려주세요."
4. 구현 중에 기획이 바뀌면(사용자가 "기획 수정해줘"라고 하는 경우 등) 이 페이지를 갱신한다. 대상 버전이 바뀌어도 이 페이지에서 고친다.

# 배포 반영 모드

## 7. 배포 완료 후 통합 기획서 반영

사용자가 특정 버전의 배포 완료를 알렸을 때만 수행한다. 버전이 명시되지 않았으면 `pubspec.yaml`의 `version`과 최신 릴리즈 태그를 확인한 뒤 "vX.Y.Z 배포 완료가 맞나요?"라고 묻는다.

1. **대상 기획안 수집** — `notion-search`로 `대상 버전: vX.Y.Z`이고 상태가 `확정 · 배포 대기`인 기획안을 전부 찾아 목록을 보여준다. 누락된 기획안이 있는지, 이번 배포에서 빠진(다음 버전으로 밀린) 것이 있는지 사용자에게 확인한다. 밀린 기획안은 대상 버전만 고치고 반영하지 않는다.
2. **배포 코드와 대조 (필수)** — 기획안과 실제로 배포된 코드는 다를 수 있다. 릴리즈 태그 `refs/tags/vX.Y.Z`(태그가 없으면 릴리즈 브랜치 `refs/heads/vX.Y.Z`) 기준으로 기획안의 각 규칙(R1, R2 …)과 데이터·마이그레이션·문구가 실제로 어떻게 구현됐는지 확인한다. 예: `git show refs/tags/vX.Y.Z:<파일>`, `git diff refs/tags/<직전 버전>..refs/tags/vX.Y.Z -- lib/`.
   - 기획과 구현이 다르면 사용자에게 묻는다: "R3은 기획에서 '최대 10개'였지만 배포 코드는 '최대 5개'입니다. 구현 쪽이 의도된 변경인가요, 버그인가요?" 의도된 변경이면 구현 기준으로 반영한다. 버그이면 통합 기획서에는 **배포된 실제 동작**을 쓰고, 버그는 별도로 알린다.
   - 통합 기획서에는 기획안의 문장이 아니라 **배포된 실제 동작**을 쓴다.
3. **최신본 재조회 & 스펙 확인** — `notion-fetch`로 통합 기획서 최신본을 다시 읽고, `notion://docs/enhanced-markdown-spec`도 읽는다.
4. **반영 diff 작성 후 승인** — 바뀔 내용을 채팅에 "절 / 변경 전 / 변경 후" 형식으로 보여주고 승인받는다.
   - 기능·정책은 해당 절(§2~§8 등) 본문에 직접 반영한다. 새 영역이면 적절한 위치에 절을 추가한다.
   - 스키마가 바뀌었으면 §7 데이터 모델 표와 `schemaVersion` 표기를 갱신한다.
   - 새로 민감한 정책이 생겼으면 §10 체크리스트에 항목을 추가한다.
   - 기획안에 기록해 둔 **기획서-코드 불일치**도 이번에 코드 기준으로 바로잡는다.
   - 상단 `**버전**`을 `v(N+1) (YYYY-MM-DD, 앱 vX.Y.Z 배포 반영)`으로 올리고, 문서 끝 `## 변경 이력` 절(없으면 생성)에 `- vN+1 (YYYY-MM-DD): 앱 vX.Y.Z 배포 반영 — 「기능A」, 「기능B」 (§3, §7 수정, §10 체크리스트 1건 추가)` 형식으로 한 줄 남긴다.
5. **부분 수정으로 반영** — `notion-update-page`로 필요한 부분만 치환·삽입한다. **페이지 전체 내용 교체는 금지**(표, callout 등 기존 블록이 손상될 수 있다). 수정 후 다시 `notion-fetch`해서 의도대로 들어갔는지, 기존 절이 훼손되지 않았는지 확인한다.
6. **기획안 상태 갱신** — 반영한 기획안 페이지의 상태를 `배포 완료 · 통합 기획서 반영됨 (통합 기획서 vN+1, YYYY-MM-DD)`으로 바꾼다. 기획과 구현이 달랐던 부분은 기획안 하단에 "배포 시 변경 사항"으로 남긴다.
7. 반영된 통합 기획서 링크와 변경 요약을 전달한다.

## 참고

- `write-prd` 스킬과의 차이: `write-prd`는 아이디어를 PRD 양식으로 빠르게 정리·발행하는 용도다. 이 스킬은 기존 정책·코드와의 정합성 검증, 모호성 제거, 배포 후 통합 기획서 반영까지 책임진다. money_mate 기능 기획에는 이 스킬을 우선 사용한다.
- 응답은 항상 한국어 존댓말로 한다.
